## 先理解两个入口

`roborsi-compile` 只编译，不连接机器人。`roborsi-execute` 不带 `--execute` 时只做 dry 检查；只有显式带该参数才进入硬件执行分支。图中的“执行前检查”包含连接之前的静态检查，以及连接之后、目标流启动之前的实测状态检查。

未通过检查就拒绝启动目标流；若已连接设备，则仍按保持清理逻辑处理。历史示例、无有效几何验证、指纹变化或状态不一致，均不能直接执行。

## 执行前检查什么

| 检查对象 | 意义 |
| --- | --- |
| 计划意图与场景 | 本轮计划绑定新鲜场景与初始状态，不能直接复用历史示例 |
| 目标流及 URDF 指纹 | 确保审阅后的轨迹和装配描述没有被更换 |
| 控制后端、物理左右臂映射 | 检查接口版本及 USB 身份，不按 CAN 名称猜测物理侧 |
| 几何与关节范围 | 使用真实装配参数验证目标流 |
| 实测初始姿态与设备状态 | 确认计划起点与现场一致，避免启动跳变 |

完整参数和操作条件以[硬件接入指南](HARDWARE.md)为准。图只描述机制，不是某台机器的现场授权。

## 连续执行中的三件事

1. **写目标：**唯一控制线程以 200 Hz 发送队列中的目标。
2. **补队列：**监督循环在队列低水位时补入固定目标流的后续点，不重新规划。
3. **读反馈与保护：**约每 20 ms 检查状态新鲜度、限位、TCP 高度、跟踪误差、非活动臂漂移、夹爪宽度及写线程健康；按事件索引执行阶段和夹爪检查。

保护存在检测延迟，不是硬实时安全控制器。`done` 不只表示最后一个点已入队：代码还等待队列耗尽和多次反馈满足收敛条件，然后记录 `stream_complete`。

## 正常结束与异常停止

两条路径都停止并 join 唯一写线程、清空待执行队列、读取一次新鲜实测状态并尝试冻结该目标，保留扭矩和夹爪。不会自动回零、松爪、断使能或续跑。

“回到初始位置”必须是计划中已有的运动阶段，不是程序退出时偷偷追加的动作。若无法 join 线程或取得新鲜状态，软件不能假装已成功保持；需要现场处理。清理失败时不能保证后续批量日志导出完成，因此持久化故障事件与实际设备状态都应核对。

大量命令和反馈记录先存在内存，正常清理后导出；少量阶段/故障事件由监督路径记录。Web 生成和查看发生在执行之后，不进入 200 Hz 控制路径。

## 任务是否成功单独判断

`stream_complete` 表示程序已走完并满足收敛条件，夹爪宽度检查只验证一个执行信号。物体是否真正进入篮筐，需要结果图像与现场确认。

将这些结果与失败原因一同复盘，修改下一轮的场景解释、关键点或夹爪策略，这才是当前版本的 RSI 过程；执行中没有自动模型重规划，也没有保护后自动重试。
